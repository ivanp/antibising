Rewriting NoiseTorch as a Tauri v2 Linux App

Date: 2026-07-27 Topic: noisetorch-tauri-rewrite Focus: Tauri v2 rewrite of NoiseTorch-ng, v1 scope Mode: repo-grounded

Seven directions that survived adversarial verification against this machine — sway/Wayland, waybar v0.15.0, PipeWire 1.6.8, WirePlumber 0.5.15. Two of the most attractive candidates were refuted by live evidence, and one verification result reframes the central architecture question the whole idea set was circling.

Codebase Context

antibising/ is an empty greenfield repo — only .git. Nothing to refactor, nothing to preserve; every decision here is a first decision. The reference implementation is NoiseTorch-ng at ../nt/: Go, immediate-mode nucular GUI, a vendored PulseAudio protocol library, RNNoise embedded as a LADSPA .so via go:embed and dumped to a temp file at runtime, CAP_SYS_RESOURCE raised via pkexec so the RT-capable module can load.

The stated v1 spec: a tray-resident Tauri v2 app; click the tray to open a window; select which input mics get noise cancelling; refresh automatically on mic hotplug; remember settings across restarts; right-click to select a mic (automatically setting it as the Linux default) or to turn the filter off entirely.

Local ground truth measured during grounding

  • Desktop is sway/wlroots on Wayland, not GNOME or KDE. The tray host is waybar v0.15.0 speaking StatusNotifierItem over D-Bus.
  • PipeWire 1.6.8, WirePlumber 0.5.15, pipewire-pulse serving the PulseAudio protocol.
  • Three physical capture sources: a Razer Seiren Mini (USB), the Meteor Lake-P built-in digital mic, and an ATH-M20xBT Bluetooth headset.
  • A module-ladspa-source is loaded right now with plugin=/usr/lib/ladspa/librnnoise_ladspa.so control=95 — and its master= device no longer exists in the graph.
  • /usr/share/pipewire/filter-chain/source-rnnoise.conf ships a complete RNNoise virtual-source preset; ~/.config/pipewire/filter-chain.conf.d/ does not exist yet.
  • The installed NoiseTorch binary connects to PipeWire 1.6.8 successfully and then enumerates zero sources.

The finding that reframes the spec

Tauri's built-in tray cannot distinguish left-click from right-click on Linux. Tauri wraps libappindicator, whose docs state the click event "is not emitted even though the icon is shown and will still show a context menu on right click." The v1 spec asks for exactly that distinction — left-click opens the window, right-click opens a menu.

But the limitation is Tauri's backend, not the protocol. Verified against waybar's own source: with ItemIsMenu = false, waybar calls Activate on left-click, ContextMenu on right-click, and SecondaryActivate on middle-click. Speaking StatusNotifierItem directly — via the ksni crate — restores the full spec. This is the difference between "the spec is impossible on Linux" and "the spec requires not using Tauri's tray."

The Honest Tray

Tray & window shell Confidence 92% Complexity Medium
Description

Drop Tauri's tray entirely. Register the StatusNotifierItem yourself with the ksni crate, reporting ItemIsMenu = false, and implement activate() → show window, menu() → the mic-selection context menu. That recovers the exact interaction the v1 spec asks for.

The second half is what makes it honest: the tray icon's state must be derived from a health check of the filter as it actually exists in the PipeWire graph — master device still present, links still attached — not from "we called load-module and it returned success." A filter whose input device vanished still reports RUNNING. Three states, not two: filtering, off, and broken — the last one is the state the current tooling never shows.

Axis
Tray & window shell
Basis

direct: waybar src/modules/sni/item.cpp — if ((ev->button == 1 && item_is_menu) || ev->button == 3) makeMenu(); else if (ev->button == 1) proxy_->call("Activate", ...). Left-click reaches Activate whenever the item does not claim to be a menu.

direct: ksni v0.3.6 exposes activate(x, y), secondary_activate(x, y), and menu(). It depends on zbus, not GTK or libappindicator, so it does not fight Tauri's event loop.

direct: Tauri's own source comment on TrayIconEvent::Click: "Linux: Unsupported. The event is not emitted even though the icon is shown."

direct: the zombie is live on this machine — module-ladspa-source with master=alsa_input.pci-0000_00_1f.3-...HiFi__Mic1__source is loaded and the filtered source reports RUNNING, while that master device returns zero matches in both pactl list short sources and pw-cli list-objects Node.

Rationale
This is the only idea that directly unblocks a stated v1 requirement that the obvious implementation path cannot deliver. And the honesty half addresses a failure the user is living with right now: a filter that reports success while producing silence costs fifteen minutes of debugging cables and app settings before anyone suspects the filter. A tray icon that can say "broken" is the cheapest possible fix for the most expensive possible failure.
Downsides
Hand-rolling SNI means owning re-registration when the tray host restarts — waybar restarts are routine under sway, and the item must re-announce itself when the D-Bus name owner reappears. Also means owning icon theming and menu construction that Tauri would otherwise provide. Health-checking on an interval or on Registry events adds a background task that must not race the UI.

Two-Layer State: Modules Actuate, Config Persists

State & persistence Confidence 90% Complexity Medium
Description

Five independent ideation frames all converged on the same architectural fork — "write a PipeWire filter-chain config file" versus "load a module at runtime, like NoiseTorch does" — and all five framed it as a choice. Verification says it is not a choice, because each mechanism can only do half the job.

The config file is durable but inert: PipeWire reads ~/.config/pipewire/filter-chain.conf.d/ once at daemon start. There is no file watcher and no pw-cli reload command. Writing a config and expecting a filter to appear does nothing until the daemon restarts. The runtime module is immediate but volatile: it applies the instant it loads and vanishes when PipeWire restarts.

So use both, deliberately. The config file is the declared state — the user's intent, written on every change, hand-editable, surviving reboot. Runtime module loading is the actuation — what makes a toggle take effect this second. A reconciler compares declared state against the live graph on startup, on PipeWire restart, and on device change, then loads whatever is missing. The config file makes the app's absence safe; the module load makes the app's presence responsive.

Axis
State & persistence
Basis

direct: pw-cli help lists load-module, unload-module, set-param, destroy — and no reload. Config under filter-chain.conf.d/ is read at daemon startup only; applying a change otherwise requires systemctl --user restart pipewire.

direct: the runtime path is proven live on this machine right now — pactl list modules short shows module-ladspa-source ... plugin=/usr/lib/ladspa/librnnoise_ladspa.so control=95, loaded, immediate, and still present after the loading process exited.

direct: module-ladspa-source is authored by Wim Taymans, PipeWire's lead — the PulseAudio-protocol path here is a native PipeWire mechanism, not a compatibility shim to be avoided.

external: the desired-state / observed-state reconciler is the Kubernetes controller pattern; it is the standard answer to "the world drifts and my declaration must win."

Rationale
This resolves the single most contested question in the candidate set, and it resolves it by rejecting the framing rather than picking a side. It also silently fixes several separate problems: PipeWire restarts no longer kill the filter invisibly, the app can exit without the filter dying, a power user can hand-edit the config, and "what should be on" has exactly one source of truth instead of being implicit in whatever modules happen to be loaded.
Downsides
Two representations of the same intent means a translation layer and a real risk of drift between them — the reconciler has to be genuinely correct, not best-effort. Config written by the app but only honored at next daemon start creates a window where the file and the graph disagree legitimately, and the UI must not present that as an error. Unloading modules the app did not load is a footgun worth guarding against.

Device Identity, Not Device Names

Device lifecycle Confidence 88% Complexity Medium
Description

NoiseTorch persists LastUsedInput as a PipeWire node name — a string that encodes the PCI path, the ALSA profile, and the port. Change USB ports, switch an ALSA profile, re-pair a Bluetooth headset, and that string no longer refers to anything. Persist hardware identity instead: device.vendor.id, device.product.id, device.bus, alsa.card_name, plus the serial when the device exposes one. Match on reconnect by identity, then resolve to whatever node name the device has this time.

Once identity is the key, "remember my settings" becomes per-device rather than global: the Razer stays filtered at threshold 95, the laptop mic gets a different threshold, the Bluetooth headset is excluded entirely — and each one reapplies automatically when it reappears. The mic list stops being a live enumeration and becomes remembered devices, present or absent, with an explicit disconnected state instead of silently vanishing.

Axis
Device lifecycle
Basis

direct: this failure is already on disk. NoiseTorch's config holds LastUsedInput = "alsa_input.pci-0000_00_1f.3-platform-skl_hda_dsp_generic.HiFi__Mic1__source", and that node does not exist in the current graph — grepping it in pactl list short sources exits 1 with zero matches.

direct: the same dead name is what the orphaned module-ladspa-source is still pointed at, which is why the zombie exists at all — name-keyed state and the zombie are the same bug seen from two ends.

direct: PipeWire node properties expose device.vendor.id, device.product.id, device.bus, and alsa.card_name — stable identity is already available, just unused.

external: NetworkManager keys connection profiles to interface MAC rather than eth0; kanshi and autorandr key display layouts to EDID rather than DP-1. Both solved this exact class of bug by moving from position-names to identity.

Rationale
"Remember the setting so it survives restarts" is a v1 requirement, and the naive implementation of it is already demonstrably broken on the target machine before a line of the rewrite is written. Getting the persistence key right is nearly free at greenfield and expensive to retrofit, because it changes the shape of the config file, the mic list model, and the hotplug handler simultaneously.
Downsides
Identity is not perfectly stable either — two identical USB mics of the same model are indistinguishable without a serial, and some devices report none. Bluetooth identity is MAC-based and survives re-pairing, but a profile switch (HSP versus A2DP) changes the node beneath the same device. Needs a defined tiebreak and a fallback to name matching rather than pretending identity is absolute.

Own the Default at the Metadata Layer

Device lifecycle Confidence 90% Complexity Low
Description

The spec says selecting a mic should automatically set it as the Linux default. The obvious implementation — pactl set-default-source — is the wrong layer and will be overruled. WirePlumber's default-node policy re-evaluates candidates and gives the node named in the default.configured.audio.source metadata a +30000 priority boost, which dwarfs every ordinary priority. Write that metadata key instead (pw-metadata / the metadata API) and WirePlumber's policy becomes the mechanism enforcing your choice rather than the thing fighting it.

Worth pairing with a deliberate consent moment: hijacking the system default microphone is an invasive act, and an app that does it silently on first launch is the app users uninstall. Ask once, then own it.

Axis
Device lifecycle
Basis

direct: /usr/share/wireplumber/scripts/default-nodes/find-selected-default-node.lua, lines 54-55: if current_configured_node == name then priority = 30000 + priority.

direct: live on this machine, pw-metadata -n default returns default.configured.audio.source = '{"name":"NoiseTorch Microphone for Razer Seiren Mini"}' — a stale NoiseTorch source that no longer exists, still sitting in the metadata primed to win the moment a node with that name appears.

external: Android's audio-routing consent dialog is the reference pattern for "an app is about to take over a system-wide input."

Rationale
Cheapest high-value item on the list — it is a different API call, not a different architecture, and it converts a race the app would lose into a policy the app wins. The stale key sitting in metadata right now also proves the cleanup obligation: whatever you write, you must be able to unwrite when the filter is turned off.
Downsides
Writing WirePlumber's configured-default is genuinely persistent system state that outlives the app, so "turn the filter off" must also mean "restore the previous configured default" — and the app has to record what that was. It is also policy-version-coupled: WirePlumber's default-node scripts are Lua on disk and have been reorganized between releases, so the key name is stable but the surrounding policy is not guaranteed to be.

Live Knobs — Params Without Reload

Filter engine Confidence 80% Complexity Low
Description

NoiseTorch's threshold slider requires unloading and reloading the filter — audio drops out for the duration, and any app holding the source may or may not recover. PipeWire's filter-graph implementation accepts SPA_PARAM_Props containing named control-port values and pushes them into the live DSP handles without touching the graph. The threshold becomes a real-time control: drag it while talking and hear the change.

The broader shape: separate parameters that can change live (control-port values) from parameters that require a rebuild (channel count, plugin choice, master device). Only the second class needs the disruptive path, and the UI should make the distinction invisible by never rebuilding when it doesn't have to.

Axis
Filter engine
Basis

direct: PipeWire spa/plugins/filter-graph/filter-graph.c handles SPA_PARAM_Props with a params struct by calling port_id_set_control_value() across the DSP handles — the live-update path exists in the daemon.

direct: the invocation shape is pw-cli s <node-id> Props '{ params = [ "VAD Threshold (%)" 80 ] }', and the filter nodes on this machine expose Props (id 2) as a writable param.

reasoned: control-port writes mutate a coefficient in place; they do not reallocate the graph, so there is no structural reason for a dropout — unlike module reload, which tears down and rebuilds every link.

Rationale
Turns the most-touched control in the app from a jarring operation into a continuous one, and it is a small change — a param write instead of an unload/load pair. It also removes the strongest argument for keeping the threshold slider out of v1.
Downsides
Runtime param writes are not persistent — they revert when PipeWire restarts, so the value must also be written to declared state (see idea 2) or it silently reverts. Verification confirmed the mechanism but could not confirm audible smoothness without disrupting live audio: whether a mid-stream coefficient change produces a click is unmeasured and should be tested early. Control-port names are plugin-specific strings, so swapping denoisers (idea 6) changes the parameter vocabulary.

The Denoiser Is a Config Field

Filter engine Confidence 85% Complexity Low
Description

NoiseTorch hardcodes RNNoise: the .so is embedded in the binary and the filter graph is built around it. Treat the denoiser as data instead — a plugin path plus a label plus a control map in the declared state. RNNoise is the default because it is cheap and shipped; DeepFilterNet becomes a two-field change rather than a fork of the audio engine.

The identity of the app stops being "the RNNoise app" and becomes "the mic filtering app," which is a materially larger product for approximately no additional code — as long as the graph builder never assumes a specific plugin's port layout.

Axis
Filter engine
Basis

direct: DeepFilterNet ships libdeep_filter_ladspa.so with labels deep_filter_mono and deep_filter_stereo, packaged on the AUR as deepfilternet-plugin-pipewire-bin — same LADSPA interface RNNoise uses, so the same graph shape hosts both.

direct: the module loaded on this machine already carries the plugin as an argument — plugin=/usr/lib/ladspa/librnnoise_ladspa.so ... label=noise_suppressor_mono. The parameterization point exists; nothing is exploiting it.

direct: PipeWire's LADSPA loader branches on plugin[0] != '/', searching LADSPA_PATH for bare names and calling dlopen() directly on absolute paths — so a bundled .so at an arbitrary path is loadable without touching environment variables.

reasoned: DeepFilterNet's quality advantage is real but it costs roughly an order of magnitude more CPU than RNNoise; on a 12-core Ultra 5 that is affordable, on older hardware it is not. Which makes it exactly the kind of decision that belongs to the user's config rather than to the binary.

Rationale
The cost is paid once, at the moment the graph builder is written, and only if it is written to be plugin-agnostic. Retrofitting plugin-independence after the graph builder has RNNoise's port layout baked into it is a rewrite of the core. This is the classic case for spending a little structure early.
Downsides
Different plugins expose different control ports, so any UI beyond a generic list of named controls has to be plugin-aware anyway — a hardcoded "Threshold" slider does not survive the swap. DeepFilterNet is not in Arch's official repos, so anything beyond RNNoise means either an AUR dependency or bundling a much larger artifact. Genuine scope risk: this is the idea most likely to grow into a plugin framework nobody asked for.

antibising-core — Headless Engine, Native Registry

Distribution & install Confidence 72% Complexity High
Description

Put every audio decision — enumeration, identity matching, graph construction, reconciliation, health checking — in a plain Rust crate with no Tauri dependency and no UI concepts. The Tauri app becomes a consumer of it, and so can a CLI, a systemd user service, and a test harness that drives the engine without a display server.

Inside that crate, talk to PipeWire through the pipewire crate's Registry rather than shelling out to pactl. Registry emits a global event per object and global_remove on disappearance — which is precisely the hotplug notification the spec's "automatic refresh when a mic is plugged or unplugged" requires, and which parsing pactl output cannot give you without polling.

Axis
Distribution & install
Basis

direct: the pipewire crate's registry documentation — "globals come and go as a result of device hotplugs or reconfiguration or other events, and the registry will send out global and global_remove events to keep the client up to date." Maintained by the PipeWire project itself.

direct: pactl subscribe produced no output across a two-second idle sample — it is an event stream with long silences, so a shell-out design degrades into either a long-lived parsed subprocess or a polling loop.

direct: NoiseTorch's device list "is populated once on PulseAudio connect and never refreshed until disconnect/reconnect" — the reference implementation's hotplug story is that it does not have one, which is exactly what the v1 spec calls out as a requirement.

reasoned: the engine is where every hard-to-reproduce bug in this app will live — zombie filters, hotplug races, reconciliation drift. Those are only testable if they can be driven without a webview.

Rationale
This is the leverage item: it does not deliver a user-visible feature, it makes ideas 2, 3, and 5 implementable and testable rather than aspirational. Ranked last because it is the one direction whose value is entirely downstream — if v1 turns out to be a weekend tool for one machine, this is over-investment.
Downsides
Highest implementation burden on the list, and the pipewire crate is a thinner, less-documented surface than shelling out to pactl — verification noted its docs.rs build is broken, so the API must be learned from source. Async lifetime management around Registry listeners in Rust is genuinely fiddly. A crate boundary drawn before the shape of the problem is known can become a boundary in the wrong place.

Rejection Summary

Forty-one candidates were generated across six frames; two were refuted outright by live verification, and the rest were either folded into a stronger survivor or cut. Two clusters were produced independently by four of the five frames each — the tray mechanism and the config-versus-module question — which is why both became survivors rather than being deduplicated away.
